## 1. Introduction

### What is the NC Parser?

The Shatter NC Parser is a specialized G-code analysis tool designed to extract metadata from CNC programs generated by the **Autodesk Fusion 360 Brother Speedio post processor** (`brother speedio.cps`). It enables advanced program management, validation, and monitoring capabilities within the Shatter platform.

**Note**: The Brother Speedio post processor used with Shatter is a **customized/forked version** of Autodesk's standard post processor, incorporating functionality from two open-source projects:
- **WCS validation**: Based on [VerifyWCS](https://github.com/toolpath/VerifyWCS) by toolpath
- **Tool length validation**: Based on work from [fusion-360-post-processors](https://github.com/ewildgoose/fusion-360-post-processors) by ewildgoose

### Why Custom Parsing?

Standard G-code files lack structured metadata. The parser extracts critical information embedded in comments and specific G-code patterns to enable:

- **Tool Validation**: Verify tool dimensions against machine ATC inventory
- **WCS Validation**: Confirm work offset positions match CAM expectations
- **Operation Tracking**: Monitor speeds/feeds used for each machining operation
- **Version Control**: Content-based deduplication using SHA-256 hashing
- **Runtime Estimation**: Calculate expected cycle times
- **Deployment Tracking**: Map programs to machine O-numbers

### Prerequisites

- **Autodesk Fusion 360** with Manufacturing workspace
- **Brother Speedio post processor** (`brother speedio.cps`)
- **Brother Speedio S700X2** CNC machine (or compatible)

### What This Guide Covers

- Required post processor configuration settings
- Detailed format specifications for parseable elements
- Parser behavior and extraction logic
- Validation features and tolerances
- Best practices for CAM programming

## 2. Post Processor Attribution

The customized Brother Speedio post processor incorporates functionality from these open-source projects:

### WCS Validation (G65 P8901)

**Source**: [toolpath/VerifyWCS](https://github.com/toolpath/VerifyWCS)

**Functionality**: Outputs a macro call (`G65 P8901`) that verifies the work coordinate system position matches between CAM and machine. This prevents crashes due to incorrect fixture setup or work offset configuration.

**Implementation**: The `verifyWCS()` function (lines 670-697) generates verification commands at the start of each work offset:

```javascript
function verifyWCS() {
  // Iterates through sections, outputs G65 P8901 for each unique WCS
  writeBlock(
    gFormat.format(65),
    "P" + 8901,
    "X" + xyzFormat.format(mcsOrigin.x),
    "Y" + xyzFormat.format(mcsOrigin.y),
    "Z" + xyzFormat.format(mcsOrigin.z),
    "E" + xyzFormat.format(getProperty("wcsTolerance", 0.01)),
    "W" + wcs
  );
}
```

### Tool Length Validation

**Source**: [ewildgoose/fusion-360-post-processors](https://github.com/ewildgoose/fusion-360-post-processors)

**Functionality**: Outputs comprehensive tool information including total length (`bodyLength + holderLength`) in the header comments, enabling validation against machine tool table data.

**Implementation**: Tool comment generation (lines 3776-3787) includes length data:

```javascript
comment += " - L=" + xyzFormat.format(tool.bodyLength) + "/" +
           xyzFormat.format(tool.bodyLength + tool.holderLength);
```

Additionally, at tool changes (lines 2129-2132), the post processor can compare CAM-defined tool length with machine tool table values:

```javascript
var camLen = xyzFormat.format(tool.bodyLength + tool.holderLength);
var tooltableLen = "#" + (toolLenBase + tool.number);
// Comparison logic for validation
```

## 3. Post Processor Setup

### Required Configuration

To generate parser-compatible G-code, configure the Brother Speedio post processor with these **critical settings**:

| Setting | Value | Purpose |
|---------|-------|---------|
| **useParametricFeed** | `true` | Enables #500-#509 feedrate macro output |
| **showNotes** | `true` | Includes operation names in comments |
| **wcsTolerance** | `0.01` (or desired) | Sets WCS validation tolerance |
| **firstFeedParameter** | `500` | Starting macro number for feedrates |
| **feedAssignmentVariable** | `"#"` | Prefix for feedrate macros |

### Post Processor Properties

In Fusion 360, access these settings via:

1. **Manufacture** workspace → **Manage** → **Post Library**
2. Select **brother speedio** post processor
3. Click **Edit** to modify properties

### Verifying Configuration

After posting a program, verify these elements are present:

- [ ] Tool definitions in header comments (e.g., `(T01 D=0.25 CR=0 ...)`)
- [ ] Posted date comment (e.g., `(DATE: SAT DEC 13 07:05:36 2025)`)
- [ ] WCS validation macro if enabled (e.g., `G65 P8901 X-21.9975 ...`)
- [ ] Operation name comments (e.g., `(ADAPTIVE1)`)
- [ ] Parametric feedrate macros (e.g., `#500=39.4 (CUTTING)`)
- [ ] Stock size comment if defined (e.g., `(X146.05 Y25.4 Z12.7)`)

#### Step 2: Add WCS Verification Function

Add the `verifyWCS()` function from the [VerifyWCS repository](https://github.com/toolpath/VerifyWCS):

```javascript
function verifyWCS() {
  if (machineConfiguration.isReceived()) {
    var checked = [];
    writeComment("-----------------------");
    writeComment("   Verify WCS Positions");
    for (i = 0; i < getNumberOfSections(); ++i) {
      var section = getSection(i);
      var wcs = section.workOffset;
      wcs = wcs == 0 ? 1 : wcs;
      wcs = wcs > 6 ? -(wcs - 6) : wcs + 53;
      if (typeof checked[wcs] == "undefined") {
        mcsOrigin = toMCSPosition(section, new Vector(0, 0, 0));
        writeBlock(
          gFormat.format(65),
          "P" + 8901,
          "X" + xyzFormat.format(mcsOrigin.x + getProperty("wcsXShift", 0)),
          "Y" + xyzFormat.format(mcsOrigin.y + getProperty("wcsYShift", 0)),
          "Z" + xyzFormat.format(mcsOrigin.z + getProperty("wcsZShift", 0)),
          "E" + xyzFormat.format(getProperty("wcsTolerance", 0.01)),
          "W" + wcs
        );
        checked[wcs] = true;
      }
    }
    writeComment("-----------------------");
    writeln("");
  }
}
```

#### Step 3: Call WCS Verification in onSection()

Add a call to `verifyWCS()` in your `onSection()` function, typically after work offset selection:

```javascript
function onSection() {
  // ... existing section setup code ...

  // Output work offset (G54, G55, etc.)
  var workOffset = currentSection.workOffset;
  if (workOffset > 0) {
    if (workOffset > 6) {
      error(localize("Work offset out of range."));
      return;
    } else {
      writeBlock(currentSection.wcs);
    }
  }

  // Call WCS verification
  verifyWCS();

  // ... continue with section code ...
}
```

#### Step 4: Modify Tool Header Comments

Update your tool header output to include the `L=bodyLength/totalLength` format:

```javascript
// In your tool header generation section (typically in onOpen())
var tools = getToolTable();

      comment += " - ZMIN=" + xyzFormat.format(zRanges[tool.number].getMinimum());
    }

    // Add tool type
    comment += " - " + getToolTypeName(tool.type);

    // ADD THIS: Tool length in format L=flute_length/total_length
    comment += " - L=" + xyzFormat.format(tool.bodyLength) + "/" +
               xyzFormat.format(tool.bodyLength + tool.holderLength);

    writeComment(comment);
  }
}
```

Ensure your post processor has parametric feedrate support configured:

## 4. Parseable Formats

### 4.1 Tool Definitions

**Location**: Header comment section (before first operation)

**Format**:
```gcode
(T## D=diameter CR=corner_radius - ZMIN=value - description - L=flute_length/total_length)
```

**Example**:
```gcode
(T01 D=0.25 CR=0 - ZMIN=1.7674 - FLAT END MILL - L=0.65/3.609)
(T03 D=0.118 CR=0.059 - ZMIN=2.004 - BALL END MILL - L=0.295/3.189)
(T21 D=0.1181 CR=0.0591 - ZMIN=2.0036 - PROBE - L=1.9685/1.9685)
```

**Extracted Fields**:
- `tool_number`: Integer (1-99)
- `diameter`: Float in inches
- `corner_radius`: Float in inches (0 for flat end mills)
- `description`: String (e.g., "FLAT END MILL", "BALL END MILL")
- `length_total`: Float in inches (second L value)

**Parser Behavior**:
- Regex: `r'\(T(\d+)\s+D=([\d.]+)\s+CR=([\d.]+)\s+-\s+ZMIN=([\d.]+)\s+-\s+([^-]+?)\s+-\s+L=([\d.]+)/([\d.]+)\)'`
- Graceful degradation: Missing tools are skipped, not errors
- Duplicates: Last occurrence wins

---

### 4.2 Posted Date

**Location**: Header comment section (typically line 3)

**Format**:
```gcode
(DATE: DDD MMM DD HH:MM:SS YYYY)
```

**Example**:
```gcode
(DATE: SAT DEC 13 07:05:36 2025)
```

**Extracted Field**:
- `posted_date`: ISO 8601 datetime with timezone

**Parser Behavior**:
- Regex: `r'\(DATE:\s*(.+?)\)'`
- Parsing: `datetime.strptime(date_str, "%a %b %d %H:%M:%S %Y")`
- Default timezone: UTC
- Graceful degradation: Missing date → `null`

---

### 4.3 WCS Offset Validation

**Location**: After G54-G59 work offset selection, before first tool call

**Format**:
```gcode
G65 P8901 X## Y## Z## E## W##
```

**Example**:
```gcode
G54
G17 G90 G94
G65 P8901 X-21.9975 Y-2.8563 Z-15.8976 E0.01 W54
```

**Extracted Fields**:
- `x`, `y`, `z`: Float positions in inches (work offset location)
- `work_offset`: Integer (54-59)
- `tolerance`: Float in inches (E parameter, default 0.01)

**Parser Behavior**:
- Regex: `r'G65\s+P8901\s+X([-\d.]+)\s+Y([-\d.]+)\s+Z([-\d.]+)(?:\s+E([\d.]+))?\s+W(\d+)'`
- Validation: Compares parsed position to machine's stored G54-G59 offset
- Graceful degradation: Missing WCS validation → skip validation, no error

**Validation Logic**:
```python
position_diff = sqrt((cam_x - machine_x)^2 + (cam_y - machine_y)^2 + (cam_z - machine_z)^2)
validation_passed = position_diff <= tolerance
```

### 4.4 Stock Size

**Location**: Header comment section (after tool definitions)

**Format**:
```gcode
(STOCK SIZE)
(X## Y## Z##)
```

**Example**:
```gcode
(STOCK SIZE)
(X146.05 Y25.4 Z12.7)
```

**Extracted Fields**:
- `x`, `y`, `z`: Float dimensions in inches

**Parser Behavior**:
- Regex: `r'\(X([\d.]+)\s+Y([\d.]+)\s+Z([\d.]+)\)'` after `(STOCK SIZE)` comment
- Graceful degradation: Missing stock size → `null`

---

### 4.5 Operation Names

**Location**: Comment immediately before tool call or operation start

**Format**:
```gcode
(OPERATION_NAME)
```

**Examples**:
```gcode
(PROBE GEOMETRY2)
(ADAPTIVE1)
(2D CONTOUR1)
(FACE2)
(HORIZONTAL1)
```

**Parser Behavior**:
- Regex: `r'^\(([A-Z0-9_\s]+)\)$'`
- Tracks most recent operation name for subsequent tool calls
- Associates operation name with speeds/feeds data
- Graceful degradation: Missing operation name → `null`

---

### 4.6 Tool Calls with Spindle Speed

**Location**: Throughout program at tool changes

**Format**:
```gcode
N## G100 T## ... S#### M3 M8
```

**Example**:
```gcode
N25 G100 T01 Z1.25 S5000 M3 M8
N70 G100 T01 Z1.25 M3 M8
N4035 G100 T03 Z1.25 S10000 M3 M8
```

**Extracted Fields**:
- `tool_number`: Integer from T parameter
- `spindle_speed`: Integer RPM from S parameter (if present)

**Parser Behavior (Modal Tracking)**:
- First occurrence: Captures spindle speed from S parameter
- Subsequent occurrences: Uses previous speed if S parameter omitted
- Tracks modal spindle speed per tool number
- Example:
  ```python
  tool_modal_spindle[1] = 5000  # N25 G100 T01 S5000
  # Later: N70 G100 T01 (no S) → uses 5000 from modal state
  ```

**Regex**: `r'N\d+\s+G100\s+T(\d+).*?(?:S(\d+))?'`

---

### 4.7 Parametric Feedrate Macros

**Location**: Immediately after tool call (within 30 lines)

**Format**:
```gcode
#50X=##.## (FEEDRATE_TYPE)
```

**Macro Number Mapping**:

| Macro | Field Name | Description |
|-------|------------|-------------|
| #500 | `feedrate_cutting` | Cutting feedrate (primary) |
| #502 | `feedrate_finish` | Finish pass feedrate |
| #503 | `feedrate_entry` | Entry/lead-in feedrate |
| #504 | `feedrate_exit` | Exit/lead-out feedrate |
| #505 | `feedrate_direct` | Rapid positioning feedrate |
| #507 | `feedrate_plunge` | Plunge/ramp feedrate |
| #508 | `feedrate_plunge` | Plunge feedrate (alternate) |
| #509 | `feedrate_transition` | Transition feedrate |

**Example**:
```gcode
(ADAPTIVE1)
N25 G100 T01 Z1.25 S5000 M3 M8
#500=39.4 (CUTTING)
#503=39.4 (ENTRY)
#504=39.4 (EXIT)
#505=787.4 (DIRECT)
#507=13.1 (PLUNGE)
#508=13.1 (PLUNGE)
#509=39.4 (TRANSITION)
```

**Extracted Fields** (per operation):
- `feedrate_cutting`: Float in inches/minute
- `feedrate_finish`: Float in inches/minute
- `feedrate_entry`: Float in inches/minute
- `feedrate_exit`: Float in inches/minute
- `feedrate_direct`: Float in inches/minute
- `feedrate_plunge`: Float in inches/minute
- `feedrate_transition`: Float in inches/minute

**Parser Behavior**:
- Scans 30 lines after each tool call
- Stops scanning at next operation comment or tool call
- Associates macros with current operation name
- Multiple operations per tool: Creates separate operation records
- Graceful degradation: Missing macros → `null` for that field

**Regex**: `r'#(50[0-9])=([\d.]+)\s*\(([A-Z]+)\)'`

## 5. Parser Capabilities

### 5.1 Extraction Process

The parser processes G-code files sequentially, extracting metadata into structured JSONB format:

```json
{
  "tools": [
    {
      "tool_number": 1,
      "diameter": 0.25,
      "corner_radius": 0,
      "description": "FLAT END MILL",
      "length_total": 3.609,
      "operations": [
        {
          "operation_name": "ADAPTIVE1",
          "spindle_speed": 5000,
          "feedrate_cutting": 39.4,
          "feedrate_entry": 39.4,
          "feedrate_exit": 39.4,
          "feedrate_direct": 787.4,
          "feedrate_plunge": 13.1,
          "feedrate_transition": 39.4,
          "feedrate_finish": null
        }
      ]
    }
  ],
  "wcs_offset": {
    "x": -21.9975,
    "y": -2.8563,
    "z": -15.8976,
    "work_offset": 54,
    "tolerance": 0.01
  },
  "stock_size": {
    "x": 146.05,
    "y": 25.4,
    "z": 12.7
  }
}
```

### 5.2 Modal State Tracking

The parser maintains modal state for:

**Spindle Speed (S parameter)**:
- First tool call: Captures explicit S value
- Subsequent calls: Uses previous S value if omitted
- Per-tool tracking: Different tools maintain independent modal states

**Example**:
```gcode
N25 G100 T01 S5000 M3 M8  → Operation 1: 5000 RPM
N70 G100 T01 M3 M8         → Operation 2: 5000 RPM (modal)
N4035 G100 T03 S10000 M3   → Operation 3: 10000 RPM
N4100 G100 T03 M3          → Operation 4: 10000 RPM (modal)
```

**Tool Number (T parameter)**:
- Tracks current tool for operation association
- Feedrate macros are associated with current tool

### 5.3 Operation Boundary Detection

Parser detects operation boundaries using:

1. **Operation name comments**: `(ADAPTIVE1)` → new operation
2. **Tool changes**: `G100 T##` → new operation
3. **Distance limit**: 30 lines after tool call → stop scanning for feedrates

This ensures feedrate macros are correctly associated with their operation.

### 5.4 Content-Based Versioning

**Hash Computation**:
- Algorithm: SHA-256
- Input: Full G-code content (UTF-8 encoded)
- Output: 64-character hexadecimal hash

**Deduplication Logic**:
```python
content_hash = hashlib.sha256(content.encode('utf-8')).hexdigest()
existing_program = db.query(Program).filter_by(content_hash=content_hash).first()

if existing_program:
    # Identical content → return existing program
    return existing_program
else:
    # New content → create new version
    version_number = get_next_version_for_filename(original_filename)
    create_new_program(content_hash, version_number, ...)
```

**Versioning Behavior**:
- Same filename + different content → increment version number
- Same filename + identical content → reuse existing program (no new version)
- Different filename + identical content → new program (version 1)

### 5.5 Runtime Estimation

**Algorithm**: Sequential line-by-line simulation

**Calculation Factors**:
- **G0/G00 (Rapid)**: Uses machine rapid rate (default: 787.4 ipm)
- **G1/G01 (Linear)**: Uses programmed feedrate (F parameter or #50X macros)
- **G2/G3 (Arc)**: Calculates arc length → time = length / feedrate
- **G4 (Dwell)**: Uses P parameter (seconds)
- **Tool changes**: Fixed time (default: 5 seconds)
- **Spindle start/stop**: Fixed time (default: 2 seconds)

**Modal Tracking**:
- Feedrate (F parameter)
- Motion mode (G0, G1, G2, G3)
- Spindle state (M3/M4 on, M5 off)
- Current position (X, Y, Z)

**Output**: `estimated_runtime_seconds` (Float)

**Limitations**:
- Does not account for acceleration/deceleration
- Assumes constant feedrate during cuts
- Tool change time is fixed estimate
- Ignores M0/M1 program stops (user-dependent)

## 6. Validation Features

### 6.1 Tool Validation

**Purpose**: Verify that tools defined in CAM match physical tools in machine ATC

**Validation Checks**:

| Check | Tolerance | Pass Criteria |
|-------|-----------|---------------|
| Diameter | ±0.00025" | \|program_diameter - machine_diameter\| ≤ 0.00025 |
| Length (min) | Configurable (default: -0.1") | machine_length ≥ required_length - 0.1 |
| Length (max) | Configurable (default: +1.0") | machine_length ≤ required_length + 1.0 |

**Validation Logic** (`/backend/app/api/programs.py`):

```python
def _validate_tool(tool, machine_data, diameter_tolerance, length_tolerance_plus, length_tolerance_minus):
    program_diameter = tool["diameter"]
    required_length = tool["length_total"]

    machine_tool = find_tool_in_atc(machine_data, tool["tool_number"])
    machine_diameter = machine_tool["diameter"]
    machine_length = machine_tool["length"]

    # Diameter check
    diameter_diff = abs(machine_diameter - program_diameter)
    diameter_match = diameter_diff <= diameter_tolerance

    # Length check
    length_min = required_length - length_tolerance_minus
    length_max = required_length + length_tolerance_plus
    length_sufficient = (length_min <= machine_length <= length_max)

    return {
        "tool_number": tool["tool_number"],
        "diameter_match": diameter_match,
        "diameter_diff": diameter_diff,
        "length_sufficient": length_sufficient,
        "machine_diameter": machine_diameter,
        "machine_length": machine_length,
        "required_length": required_length
    }
```

**Validation Results**:
- **Pass**: Green indicator, ready for deployment
- **Warning**: Yellow indicator, review recommended
- **Fail**: Red indicator, cannot deploy

**Example Output**:
```json
{
  "tool_validation": {
    "passed": true,
    "errors": [],
    "warnings": [],
    "tool_checks": [
      {
        "tool_number": 1,
        "diameter_match": true,
        "diameter_diff": 0.0001,
        "length_sufficient": true,
        "machine_diameter": 0.25,
        "machine_length": 3.610,
        "required_length": 3.609
      }
    ]
  }
}
```

### 6.2 WCS Offset Validation

**Purpose**: Verify that CAM work offset positions match machine's stored G54-G59 offsets

**Validation Check**:
- Calculates 3D Euclidean distance between CAM position and machine offset
- Compares distance to tolerance (E parameter from G65 P8901, default 0.01")

**Validation Logic**:

```python
def _validate_wcs(wcs_offset, machine_data):
    cam_x = wcs_offset["x"]
    cam_y = wcs_offset["y"]
    cam_z = wcs_offset["z"]
    work_offset = wcs_offset["work_offset"]  # 54-59
    tolerance = wcs_offset["tolerance"]  # default 0.01

    machine_offset = get_machine_work_offset(machine_data, work_offset)
    machine_x = machine_offset["x"]
    machine_y = machine_offset["y"]
    machine_z = machine_offset["z"]

    position_diff = sqrt(
        (cam_x - machine_x)**2 +
        (cam_y - machine_y)**2 +
        (cam_z - machine_z)**2
    )

    validation_passed = position_diff <= tolerance

    return {
        "work_offset": work_offset,
        "position_diff": position_diff,
        "tolerance": tolerance,
        "validation_passed": validation_passed,
        "cam_position": {"x": cam_x, "y": cam_y, "z": cam_z},
        "machine_position": {"x": machine_x, "y": machine_y, "z": machine_z}
    }
```

**Example Output**:
```json
{
  "wcs_validation": {
    "passed": true,
    "work_offset": 54,
    "position_diff": 0.0023,
    "tolerance": 0.01,
    "cam_position": {"x": -21.9975, "y": -2.8563, "z": -15.8976},
    "machine_position": {"x": -21.9980, "y": -2.8560, "z": -15.8975}
  }
}
```

**Common Failure Causes**:
- Work offset not set on machine
- Incorrect fixture setup (probe position changed)
- CAM model origin different from physical setup
- Tolerance too tight for fixturing repeatability

## 7. Best Practices

### 7.1 CAM Programming Guidelines

**Tool Naming**:
- Use consistent tool descriptions: `FLAT END MILL`, `BALL END MILL`, `CHAMFER MILL`
- Avoid special characters in tool names
- Keep descriptions concise (under 50 characters)

**Operation Naming**:
- Use UPPERCASE with numbers: `ADAPTIVE1`, `CONTOUR2`, `FACE1`
- Avoid spaces in operation names (use underscores if needed)
- Keep names under 30 characters
- Use consistent naming conventions across programs

**Work Offset Setup**:
- Always enable WCS validation in post processor
- Set appropriate tolerance (0.01" typical, 0.001" for precision work)
- Verify G54-G59 offsets on machine match CAM setup
- Document fixture setup procedures

**Stock Definition**:
- Always define stock size in Fusion 360 Setup
- Use actual stock dimensions, not model bounds
- Include stock size comment in post processor output

### 7.2 Post Processor Configuration

**Required Settings Checklist**:
- [x] `useParametricFeed = true`
- [x] `showNotes = true`
- [x] `wcsTolerance = 0.01` (or appropriate value)
- [x] `firstFeedParameter = 500`
- [x] `feedAssignmentVariable = "#"`

**Optional But Recommended**:
- [x] Enable tool change comments
- [x] Enable operation comments
- [x] Include posted date in header
- [x] Output stock size comment

### 7.3 Troubleshooting Parsing Issues

**Tools Not Detected**:
- Verify tool comment format matches specification
- Check for special characters in tool description
- Ensure `D=`, `CR=`, `L=` parameters are present
- Validate numeric values are properly formatted

**Operations Missing Feedrates**:
- Confirm `useParametricFeed = true` in post processor
- Check that feedrate macros (#500-#509) are output
- Verify macros appear within 30 lines of tool call
- Ensure operation comments are present

**WCS Validation Failing**:
- Check G65 P8901 line is present in G-code
- Verify work offset is set on machine (G54-G59)
- Confirm tolerance is appropriate for setup
- Validate X/Y/Z values match fixture setup

**Runtime Estimation Inaccurate**:
- Check feedrate macros are being used in program
- Verify rapid rate matches machine capability
- Confirm tool change time estimates are reasonable
- Note: Estimation is approximate, actual time varies

### 7.4 Version Control Best Practices

**Filename Conventions**:
- Use descriptive names: `PART-123_OP1.NC`, `FIXTURE-A_FACE.NC`
- Include operation number for multi-op parts: `_OP1`, `_OP2`
- Avoid spaces in filenames (use underscores or hyphens)

**Change Management**:
- Make meaningful changes, not trivial formatting edits
- Add comment describing change reason in CAM before posting
- Verify version number increments for actual content changes
- Document why previous versions were replaced

**Deployment Workflow**:
1. Post program from Fusion 360
2. Upload to Shatter (automatic validation)
3. Review validation results
4. Deploy to machine O-number
5. Run first article with monitoring
6. Document any issues or adjustments needed

### 8.2 G-Code Pattern Reference

| Element | Regex Pattern | Example |
|---------|---------------|---------|
| Tool Definition | `\(T(\d+)\s+D=([\d.]+)\s+CR=([\d.]+)...\)` | `(T01 D=0.25 CR=0 ...)` |

| WCS Validation | `G65\s+P8901\s+X([-\d.]+)...` | `G65 P8901 X-21.9975 Y-2.8563 Z-15.8976 E0.01 W54` |
| Stock Size | `\(X([\d.]+)\s+Y([\d.]+)\s+Z([\d.]+)\)` | `(X146.05 Y25.4 Z12.7)` |
| Operation Name | `^\(([A-Z0-9_\s]+)\)$` | `(ADAPTIVE1)` |
| Tool Call | `N\d+\s+G100\s+T(\d+).*?(?:S(\d+))?` | `N25 G100 T01 S5000 M3 M8` |
| Feedrate Macro | `#(50[0-9])=([\d.]+)\s*\(([A-Z]+)\)` | `#500=39.4 (CUTTING)` |
